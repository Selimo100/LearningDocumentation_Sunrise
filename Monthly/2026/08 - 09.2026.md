Auch in _Journey_ habe ich nochmals einige letzte Verbesserungen vorgenommen, da das Projekt nun zunehmend von Boris und weiteren Personen verwendet wird.

Unter anderem habe ich begonnen, die Anwendung stärker auf die verschiedenen Berufsgruppen auszurichten. Ein Benutzer kann nun für **mehrere Berufe gleichzeitig verantwortlich** sein, anstatt nur einer fixen Kombination zugeordnet zu werden. Dadurch kann beispielsweise ein Praxisbildner gleichzeitig Informatik und KV betreuen.

Zusätzlich habe ich die Begriffe innerhalb der gesamten Anwendung vereinheitlicht. Bezeichnungen wie „Student“, „Learner“ und verschiedene Varianten von „Lernende“ wurden konsequent durch **Apprentice** ersetzt. Auch Rollenbezeichnungen werden nun verständlich dargestellt und nicht mehr als technische Enum-Werte angezeigt.

Weitere Verbesserungen waren unter anderem:

- bessere Darstellung offener Fälle für Revisoren

- übersichtlichere Bonusansichten
- bessere Auswahl der Reports für die Bonusberechnung
- Modulcode vor dem Fachnamen
- übersichtlichere Review-Widgets
- rollenabhängige Edit-Dialoge
- stabileres Löschen von Benutzern
- verbesserter Subject Import
- einheitliche Dialoge und Interaktionen

Eine kleine, aber für die Mediamatiker wichtige Anpassung war ausserdem die **Erhöhung der Upload-Grösse**. Ihre Dokumentationen werden häufig mit InDesign erstellt und sind dadurch teilweise deutlich grösser als klassische Dokumente. Nachdem sie mich darauf angesprochen hatten, habe ich die Limite entsprechend angepasst.

### 📚 Was habe ich gelernt?

Diese Woche war weniger davon geprägt, komplett neue Technologien zu lernen, sondern vielmehr davon, **bestehende Dinge sauber abzuschliessen und für andere nutzbar zu machen**.

Bei Service Fulfillment habe ich nochmals gemerkt, wie wertvoll eine gute Abschlussdokumentation ist. Vieles, was beim ersten Setup sehr mühsam war, kann für die nächste Person deutlich einfacher werden, wenn Zugänge, Tickets und Stolpersteine sauber dokumentiert sind.

Bei der Vorbereitung für die neuen Lernenden habe ich mich intensiv damit beschäftigt, **wie ich Wissen vermitteln möchte**. Dabei habe ich gemerkt, dass ein guter Einstieg nicht bedeutet, möglichst viele Informationen in möglichst kurzer Zeit weiterzugeben. Viel wichtiger ist eine sinnvolle Reihenfolge und dass die Lernenden verstehen, weshalb sie etwas brauchen.

Besonders beim DAL-Start möchte ich versuchen, nicht einfach zu sagen:

> „Hier ist Git, hier ist OKD, hier ist der Test-Server.“

sondern zuerst den Zusammenhang zu erklären:

```text
Code schreiben
→ Git verwenden
→ Portfolio erstellen
→ auf Test-Server deployen
→ später auf OKD deployen
```

Dadurch ergibt jeder Input einen Sinn und baut auf dem vorherigen auf.

Bei Journey habe ich nochmals gemerkt, wie stark sich Anforderungen verändern, sobald eine Anwendung tatsächlich von mehreren Berufsgruppen und Personen verwendet wird. Dinge, die für Informatiker logisch sind, müssen nicht automatisch für Mediamatiker, KV oder andere Berufe passen.

Die Anpassung der Upload-Grösse war dafür ein gutes Beispiel: Technisch ist es nur eine kleine Änderung, für die betroffenen Lernenden macht sie die Anwendung aber deutlich praktischer.

Besonders wichtig war für mich diesmal das Testing mit **Spider selbst**. Ich habe dadurch nochmals klar gesehen, dass ein Endpoint nicht wirklich fertig getestet ist, nur weil er im eigenen Service funktioniert. Entscheidend ist auch, ob der tatsächliche Consumer die Schnittstelle wie vorgesehen verwenden kann.

Der komplette Weg meiner Building-IDs API war damit für mich rückblickend:

```
Anforderung verstehen
→ bestehende Architektur analysieren
→ API designen
→ gRPC Endpoint implementieren
→ lokal testen
→ Development Environment testen
→ OpenShift testen
→ Code Review
→ Integration mit Spider testen
→ Production Release
```

Dadurch habe ich bei Service Fulfillment erstmals einen sehr vollständigen **Enterprise-Feature-Lifecycle** miterlebt – von der ersten Analyse bis kurz vor den produktiven Release.

## 📌 Erkenntnisse & Aha-Momente

- Ein gutes Onboarding braucht einen roten Faden und nicht einfach eine Liste von Tools.
- Dokumentation ist besonders wertvoll, wenn sie einer anderen Person konkrete Arbeit erspart, wenn man die Abteilung wechselt.
- Software muss sich an die Benutzer anpassen und nicht umgekehrt.
- Unterschiedliche Berufsgruppen haben unterschiedliche Anforderungen an dieselbe Plattform.
- Kleine UX-Änderungen können für die tatsächlichen Benutzer einen grossen Unterschied machen.
